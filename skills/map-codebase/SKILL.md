# Map codebase

This is the entry point. The user points at a codebase and you produce a complete map a new engineer can read in an afternoon. You drive the pipeline from here and delegate each part to a focused skill. The base method for every step is [explore-codebase](../explore-codebase/SKILL.md).

Full ordered pipeline with the reasoning per phase: [references/workflow.md](references/workflow.md).

Apply the `writing-skills` plugin's `writing-style` and `write-tech-doc` skills to every doc you write. If that plugin is not installed, keep the prose plain: short sentences, active voice, no em dashes.

## Before you start

1. Confirm the target repo path and, for a monorepo, the package or app to focus on.
2. Size it. Count files by language so you pick the right depth (see explore-codebase).
3. Create `docs/codebase-map/` in the target repo.

## The pipeline

Run these in order. The later steps reuse what the earlier ones found, so the order matters. Pause after each step so the user can redirect or skip a part.

1. **Tech stack.** [inventory-tech-stack](../inventory-tech-stack/SKILL.md) reads the manifests and names the languages, frameworks, and tooling. This frames everything after it.
2. **Architecture.** [map-architecture](../map-architecture/SKILL.md) maps the components, layers, and boundaries.
3. **Dependencies.** [map-dependencies](../map-dependencies/SKILL.md) covers external packages and the internal module graph.
4. **APIs.** [map-apis](../map-apis/SKILL.md) lists the APIs the code creates and the APIs it calls.
5. **Data model.** [map-data-model](../map-data-model/SKILL.md) maps entities, schemas, and relationships.
6. **Flows.** [trace-flows](../trace-flows/SKILL.md) traces the key flows end to end. Do this after the four maps above, because a flow crosses all of them.
7. **Config and env.** [map-config-and-env](../map-config-and-env/SKILL.md) records the config surface, names only.
8. **Diagrams.** [draw-diagrams](../draw-diagrams/SKILL.md) turns the maps and flows into mermaid diagrams.
9. **Onboarding guide.** [write-onboarding-guide](../write-onboarding-guide/SKILL.md) writes the getting-started tour that points a new engineer at all of the above.

## Build the index

When the docs exist, write `docs/codebase-map/README.md` as the index. It states what the system does in two sentences, then links every generated doc with a one-line description. This is the front door of the map.

```
# Codebase map: <project name>

<Two-sentence description of what the system is and does.>

Generated by codebase-cartography on <date> against commit <sha>.

## Start here
- [Onboarding guide](onboarding.md): read this first.

## The map
- [Architecture](architecture.md): components, layers, boundaries.
- [Tech stack](tech-stack.md): languages, frameworks, tooling.
- [Dependencies](dependencies.md): external packages and internal module graph.
- [APIs](apis.md): endpoints created and services called.
- [Data model](data-model.md): entities, schemas, relationships.
- [Flows](flows.md): key request and data flows, traced end to end.
- [Config and env](config-and-env.md): configuration surface.
- [Diagrams](diagrams.md): architecture, sequence, dependency, and ER diagrams.
```

## Keep it usable

- The map is for a human who is new. Lead every doc with the shape, then the detail.
- Anchor claims to code with `path:line` so a reader can verify and jump.
- Stamp the commit sha and date on the index. A map without a version rots silently.
- Deliver the whole set at low resolution before you deepen any one part.

## Common mistakes to avoid

- Running the steps out of order. Flows and diagrams need the maps that come before them.
- Producing one perfect doc and skipping the rest. The value is the complete map.
- Dumping all nine docs in one message. Pause between steps.
- Writing prose with no `path:line` anchors. A map you cannot verify is a guess.
- Leaving the index out. Without it the reader has nine files and no front door.
